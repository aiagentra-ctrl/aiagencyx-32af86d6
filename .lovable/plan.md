# Disaster-Recovery Package for the Backend

Goal: one folder in the repo that can rebuild the entire backend on a brand-new project, so recovery is "create project → run package → swap URL/keys → done".

## What gets added

A new top-level `recovery/` folder:

```text
recovery/
  README.md                  restore guide, step by step
  sql/
    01_extensions.sql        pgvector + required extensions
    02_schema.sql            all 60+ tables, columns, defaults, FKs, indexes, uniques
    03_functions.sql         all custom DB functions (security-definer ones incl. search_path)
    04_triggers.sql          every trigger, in dependency order
    05_grants_rls.sql        GRANTs + ENABLE RLS + every policy, per table
    06_storage.sql           storage buckets + bucket policies (currently none — file documents this)
    07_seed_config.sql       config/content rows the product needs to run
    99_verify.sql            post-restore checks (object counts, RLS coverage, seeded rows)
  restore.sh                 runs the SQL files in order against a target DB URL
  MANIFEST.md                inventory: tables, functions, triggers, policies, 54 edge functions,
                             secrets list, env vars, third-party integrations
```

## Contents in detail

**Schema (02):** every table currently in the production database, generated by auditing the live catalog — columns, types, defaults, not-null, primary keys, foreign keys, unique constraints, and all indexes including the pgvector embedding indexes on `products`, `property_listings`, `knowledge_base_entries`.

**Functions (03) / Triggers (04):** all custom functions — `has_role`-style helpers, `cancel_followups_on_reply`, `cancel_followups_on_booking`, `on_link_event_track_prospect`, `on_incoming_message_track`, `mirror_demo_lead_to_prospect`, `match_products_hybrid`, `match_listings_hybrid`, `match_kb_entries`, `get_best_send_time`, the pipeline lock functions and the `touch_*` timestamp functions — plus each trigger that binds them. pgvector's own C functions are provided by the extension and are not re-declared.

**RLS + grants (05):** exact policy definitions read from the live catalog, plus the GRANT block each table needs (`authenticated`, `service_role`, and `anon` only where a policy allows public reads — e.g. public demo pages and chatbots).

**Seed data (07):** the configuration the product cannot run without — `reply_templates`, `inbox_prompts`, `node_prompts`, `follow_up_templates`, `followup_rules`, `followup_settings`, `follow_up_sequences_templates` + `follow_up_steps`, `variable_fallbacks`, `industry_templates`, `site_settings`, `ecommerce_landing_template`. Written as idempotent upserts. Operational/lead data (prospects, messages, demos, tracking) is intentionally excluded — that is a data restore, not a system restore, and the README explains how to bring it across separately if needed.

**Edge functions:** all 54 already live in `supabase/functions/` and deploy from the repo, so the package documents them rather than duplicating them — the MANIFEST lists each function, whether it is public/webhook-facing, and which secrets it needs.

**Secrets and env:** MANIFEST lists every required secret (`OPENROUTER_API_KEY`, `FIRECRAWL_API_KEY`, `VAPI_API_KEY`, `MANYREACH_API_KEY`, `INBOX_WEBHOOK_SECRET`, `NETLIFY_*`, `SITE_URL`, `SITE_DOMAIN`, plus the auto-provided `SUPABASE_*` ones) and the three frontend env vars in `.env` that must be swapped. It also flags the post-restore manual steps: re-point the ManyReach webhook URL and any Netlify/VAPI callbacks at the new project ref, and reconnect Firecrawl.

**Auth:** the product's admin panel uses a shared admin key, not end-user auth, so the auth section documents the required settings (providers off unless enabled, site URL / redirect URLs to set) rather than pretending they are SQL.

## Verification

`99_verify.sql` compares object counts against the manifest and fails loudly on any missing table, policy or trigger. I will run the whole package against a scratch database in the sandbox to prove it executes clean from zero.

Note: I cannot create a real second cloud project from here, so "tested on a fresh project" means tested on a fresh empty Postgres with the same extensions — the README includes the exact commands for you to run it against a real new project.
